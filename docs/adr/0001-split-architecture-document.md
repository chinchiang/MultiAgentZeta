# ADR-0001：架構文件拆分為四份並為條文編號

- **狀態**：已採納（v1.4.0）
- **日期**：2026-10-31

## 背景

到 v1.3.6 為止，設計只有一份文件 `docs/research/vibe-coding-multiagent-testing-toolkit-architecture-v1.3.md`，約 1,500 行。規範性條文、研究證據、設計理由與審查處置紀錄混在一起，造成三個問題：

1. 條文沒有編號，第 12.2 節的驗收條件無法逐條對應。
2. 每輪修訂都要在大量說明文字中找條文，交叉引用容易漏改（v1.3.2 曾需另補 commit）。
3. 無法回答「原型 v0.1 必須做哪些控制」。

## 決定

- 拆成四份文件，放在 `docs/toolkit/`：規格 `spec.md`、設計說明 `design-notes.md`、審查處置紀錄 `review-log.md`、《v0.1 最小範圍》 `v0.1-scope.md`。
- 四份**共用一個版本號**，任何一份改動時一起升版；拆分後第一版為 v1.4.0。
- 規格條文採 `TK-<領域>-<三位數字>` 編號，一條對應一個可獨立驗收的要求；用語分「須／不得／宜／可」四級。
- 每條附驗收方式與 v0.1 標記；驗收表改為驗收群組，並附追溯表。
- 定義類內容不編號；術語集中在 repo 根目錄的 `GLOSSARY.md`。
- v1.3.6 原檔凍結保留，作為舊審查意見引用章節的依據。

## 考慮過的其他做法

- **各文件獨立版本號**：可減少無關升版，但要另外維護文件組合對照表；使用者選擇共用版本號，降低對照成本。
- **每句「應／不得」各給一個編號**：會產生兩三百條，且許多只是同一要求的補充說明，不採用。
- **每小節一個編號**：太粗，驗收無法逐項對應，不採用。
- **刪除舊檔**：Git 歷史仍可查，但舊審查意見引用的章節不易找，不採用。

## 影響

- 之後的修訂依 `docs/toolkit/README.md` 的檢查清單進行。
- 規格中的驗收群組表與附錄 A 由條文產生，改條文後須重新產生。
- 條文數量比原先預估多（實際為 225 條），v0.1 範圍須逐條確認。
