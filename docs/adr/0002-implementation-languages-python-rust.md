# ADR-0002：工具包以 Python 與 Rust 實作

- **狀態**：已採納（v1.4.6）
- **日期**：2026-11-01
- **修訂**：v1.4.7 補記選擇 Rust 的主要原因、所有權與借用規則的說明（[R58]），以及 `unsafe` 的使用原則

## 背景

到 v1.4.5 為止，設計說明 §5.1 只把「受支援的 Python 版本」列為工作流程的候選，沒有規定整個工具包的實作語言。原型 v0.1 已開始實作：#2 的 E1 環境模組（`toolkit/e1.py`）與文件工具（`docs/toolkit/tools/build.py`）都以 Python 寫成。後續工作票會加入沙盒（#6）、機密遮罩（#15）、預算帳本（#18）等位於信任邊界上的元件，需要先決定實作語言，避免每張票各自選擇。

### Rust 的記憶體管理方式

以下摘自 Rust 官方教材（設計說明參考資料 [R58]）。這些是 Rust 語言的設計保證，不是本工具包的實測結果。

- **所有權（ownership）**：每個值都有一個擁有者，同一時間只能有一個擁有者；擁有者離開作用域時，值就被釋放。記憶體不靠執行期的垃圾回收，也不由程式設計師手動配置與釋放，而是由這組規則管理，由編譯器檢查，違反任一規則時程式無法編譯。教材也說明所有權相關功能不會拖慢執行期（[R58] §4.1）。
- **借用（borrowing）**：存取資料而不取得所有權時使用參考。任何時刻，一筆資料只能有一個可變參考，或任意多個不可變參考；參考必須永遠有效。因此編譯器能在編譯期防止資料競爭（data race）與懸置參考（dangling reference）（[R58] §4.2）。
- **界線**：上述記憶體安全保證在 unsafe Rust 中不會被強制執行，但 `unsafe` 不會關閉借用檢查（[R58] §20.1）。所以這些保證只在 unsafe 區塊以外完整成立。

## 決定

- 工具包本身的程式以 **Python** 與 **Rust** 實作，由專案負責人指定。選擇 Rust 的主要原因是它在記憶體管理方面的能力。
- **Python 是預設語言**：工作流程與控制器、資料契約、模型適配、環境建置、報告與測試。
- **Rust 用於下列條件的元件**：主要是需要記憶體安全保證的元件，其次是需要單一靜態執行檔或低延遲的元件，通常位於信任邊界上。例如沙盒啟動與中止路徑、送出前的機密掃描與遮罩，以及解析不可信輸入的元件。是否採用 Rust 在各工作票的測試計畫中逐一確認，不預先指定。
- **Rust 元件原則上不使用 `unsafe`**，否則就失去選擇 Rust 的主要理由。必須使用時（例如呼叫作業系統介面），在該工作票的審查中逐處說明理由與範圍。
- 以下不受此限：
  - **受測樣本專案**：它們是測試對象，依受測技術棧撰寫（例如 Next.js 用 TypeScript）。
  - **外部工具**：例如 Supabase CLI、Docker、Gitleaks，依支援矩陣固定版本使用。
- Python 與 Rust 的工具鏈版本列入支援矩陣（`TK-SCP-001`）並固定來源與摘要（`TK-SUP-002`）。

## 未決事項

- Python 與 Rust 的銜接方式：獨立執行檔加上結構化輸入輸出，或 PyO3 擴充模組。這會影響隔離方式與測試接縫，所以在第一個 Rust 元件的工作票中決定，並另寫 ADR 記錄。

## 考慮過的其他做法

- **只用 Python**：依賴最少，現有程式與測試都是 Python。專案負責人決定同時採用 Rust，主要考量是 Rust 在記憶體管理方面的能力。
- **TypeScript／Node.js**：和受測技術棧相同。未採用，因為專案負責人指定的是 Python 與 Rust。
- **每張工作票自行選擇語言**：彈性最大，但工具鏈、支援矩陣與審查負擔會分散。不採用。

## 影響

- 設計說明 §5.1 加入「實作語言」段落，表中的工具與函式庫仍然是候選。
- 第一個 Rust 元件出現時，要安裝 Rust 工具鏈並固定在支援矩陣中，CI 也要加入對應的建置與測試。
- 現有的 Python 程式（`toolkit/e1.py`、`docs/toolkit/tools/build.py`）不需要改寫。
