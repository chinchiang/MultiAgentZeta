# ADR-0002：工具包以 Python 與 Rust 實作

- **狀態**：已採納（v1.4.6）
- **日期**：2026-11-01

## 背景

到 v1.4.5 為止，設計說明 §5.1 只把「受支援的 Python 版本」列為工作流程的候選，沒有規定整個工具包的實作語言。原型 v0.1 已開始實作：#2 的 E1 環境模組（`toolkit/e1.py`）與文件工具（`docs/toolkit/tools/build.py`）都以 Python 寫成。後續工作票會加入沙盒（#6）、機密遮罩（#15）、預算帳本（#18）等位於信任邊界上的元件，需要先決定實作語言，避免每張票各自選擇。

## 決定

- 工具包本身的程式以 **Python** 與 **Rust** 實作，由專案負責人指定。
- **Python 是預設語言**：工作流程與控制器、資料契約、模型適配、環境建置、報告與測試。
- **Rust 用於下列條件的元件**：需要記憶體安全保證、單一靜態執行檔或低延遲，且通常位於信任邊界上。例如沙盒啟動與中止路徑、送出前的機密掃描與遮罩，以及解析不可信輸入的元件。是否採用 Rust 在各工作票的測試計畫中逐一確認，不預先指定。
- 以下不受此限：
  - **受測樣本專案**：它們是測試對象，依受測技術棧撰寫（例如 Next.js 用 TypeScript）。
  - **外部工具**：例如 Supabase CLI、Docker、Gitleaks，依支援矩陣固定版本使用。
- Python 與 Rust 的工具鏈版本列入支援矩陣（`TK-SCP-001`）並固定來源與摘要（`TK-SUP-002`）。

## 未決事項

- Python 與 Rust 的銜接方式：獨立執行檔加上結構化輸入輸出，或 PyO3 擴充模組。這會影響隔離方式與測試接縫，所以在第一個 Rust 元件的工作票中決定，並另寫 ADR 記錄。

## 考慮過的其他做法

- **只用 Python**：依賴最少，現有程式與測試都是 Python。專案負責人決定同時採用 Rust，以便在信任邊界上的元件有更多選擇。
- **TypeScript／Node.js**：和受測技術棧相同。未採用，因為專案負責人指定的是 Python 與 Rust。
- **每張工作票自行選擇語言**：彈性最大，但工具鏈、支援矩陣與審查負擔會分散。不採用。

## 影響

- 設計說明 §5.1 加入「實作語言」段落，表中的工具與函式庫仍然是候選。
- 第一個 Rust 元件出現時，要安裝 Rust 工具鏈並固定在支援矩陣中，CI 也要加入對應的建置與測試。
- 現有的 Python 程式（`toolkit/e1.py`、`docs/toolkit/tools/build.py`）不需要改寫。
